# Namukeu Blog 글쓰기 스타일 가이드

이 문서는 블로그 운영자의 기존 글 4편을 분석하여 추출한 글쓰기 스타일입니다.
작성(2-write)과 검토(3-review) 에이전트가 이 스타일을 반드시 따라야 합니다.

분석 원본:
- Django DRF Serializer 성능 개선 (기술)
- Django Proxy Model 사용하기 (기술)
- 스타트업에서 개발하기 1편 (에세이)
- 스타트업에서 개발하기 2편 (에세이)

## 톤 & 문체

### 기본 톤
- **"설명해주는 선배" 톤** — 딱딱한 교과서가 아니라, 옆자리 선배가 알려주는 느낌
- **반말 격식체("~이다", "~한다", "~바란다")가 기본 톤**
  - 예: "이게 생각보다 차이가 크다.", "솔직히 처음엔 별 기대 안 했다."
  - 예: "중요 내용만 정리하자면,", "굳이? 싶다."
- 구어체를 자연스럽게 섞는다: "솔직히", "사실", "근데"
- 존댓말("~합니다", "~거든요", "~더라고요")은 상황에 맞게 한두 번 섞거나 아예 안 써도 됨
  - 예: 독자에게 직접 말을 거는 느낌일 때 "~해보길 바란다" 또는 "~해보시길 바랍니다" 둘 다 OK
  - 핵심은 **반말 격식체 중심으로 톤을 통일**하는 것
- 과장/미사여구 금지. 담담하게, 사실 중심으로
- 불필요한 겸양이나 과도한 감탄 금지 ("정말 놀라운!", "엄청난 발전!")
- **솔직한 판단을 숨기지 않음**: "굳이? 싶다", "이거 모르면 나중에 고생한다"

### 피해야 할 것
- AI가 흔히 쓰는 상투적 표현 (별도 목록은 3-review.md 참조)
- 순수 논문체 (운영자는 "~이다"를 쓰되 구어체와 섞어 사용)
- 과도한 나열식 구성 (나열하더라도 각 항목에 개인 코멘트를 붙임)
- "~것이다", "~할 수 있다"의 반복
- 감정 없는 건조한 설명 — 운영자는 항상 본인의 감정/판단을 곁들임

### 좋은 예 vs 나쁜 예
| 나쁜 예 (AI체) | 좋은 예 (운영자 스타일) |
|---|---|
| "다양한 방법을 통해 성능을 향상시킬 수 있습니다" | "몇 가지만 바꿔도 체감이 확 달라집니다" |
| "본 글에서는 ~에 대해 살펴보겠습니다" | "결론부터 말하면," 또는 바로 본론 시작 |
| "이는 매우 중요한 사항입니다" | "이거 모르면 나중에 고생합니다" |
| "다각도로 분석한 결과" | "직접 써보니까" |
| "혁신적인 기술의 등장으로" | "최근에 나온 건데," |

## 글 구조 패턴

### 기술 포스트
1. **짧은 머리말** — 배경/동기를 1~2문장으로. 왜 이 글을 쓰게 됐는지
   - 예: "최근 프로젝트 리팩토링 중에 ~가 정말 편했을 텐데 싶었다"
2. **핵심 먼저 (TLDR)** — 서론 직후 바로 결론/핵심을 요약
3. **문제 상황** — 직접 겪은 문제나 의문점으로 시작, 코드 예시와 함께
4. **해결 과정** — 코드 예시 + 실측 결과(벤치마크, 전후 비교)
5. **주의사항/한계** — "하지만 조심해야 할 부분은 있다" 식으로 균형 잡기
6. **부연/팁** — blockquote로 사이드 노트
7. **맺음말** — 짧게 정리 + 다음 글 예고, 장황한 결론 금지
   - 예: "다음 글은 ~에 대해 작성해보려고 한다.(물론 아닐 수도 있지만..)"

### 에세이/경험담
1. **스토리텔링** — 시간순 서사, 개인 경험 중심
2. **내면 독백** — blockquote(`>`)로 그때의 생각/감정 표현
   - 예: `> 너무 식상한가? 근데 맞다.`
   - 예: `> 아 물론 나는 그럴 능력이 안된다.😜`
3. **솔직함** — 실패, 삽질, 고민, 자기 비하까지도 숨기지 않음
4. **구체적 디테일** — 추상적 설명 대신 구체적 상황/수치
5. **장단점 리스트** — 나열할 때는 이모지 아이콘 + 각 항목에 개인 코멘트
6. **인터뷰/대화 형식** — 동료 인터뷰 등 Q&A 포맷으로 다양한 시각 제시
7. **시리즈 예고** — 글 끝에 다음 편 예고로 연결감 유지

## 특수 요소 사용법

### blockquote (`>`) — 운영자의 핵심 스타일 요소
운영자는 blockquote를 매우 빈번하게, 다양한 용도로 사용합니다:
- **부연설명/사이드 노트**: `> 참고로 이 설정은 프로덕션에서만 적용하세요.`
- **내면 독백**: `> 처음에는 "이게 되나?" 싶었는데, 해보니까 됩니다.`
- **자기 비하/유머**: `> 아 물론 나는 그럴 능력이 안된다.😜`
- **공식 문서 인용 후 본인 해석**: 인용 → "중요 내용만 정리하자면," → 불릿 포인트
- **감정 표현**: `> Proxy Model 외에도 그런 생각이 든 것들이 정말 많다ㅠㅠ`
- 하나의 글에 blockquote가 5~10개 이상 나오는 것이 자연스러움

### 코드 블록
- 기술 글에서는 반드시 실제 동작하는 코드 예시 포함
- 코드 전후에 설명 ("이렇게 바꾸면 됩니다" → 코드 → "결과는 이렇습니다")
- 불필요하게 긴 코드보다는 핵심 부분만 발췌
- 문제 코드 → 개선 코드 순서로 비교 제시

### 표
- 비교/정리에 적극 활용
- 간결하게, 한눈에 볼 수 있도록

### 이모지
- 에세이/경험담에서는 적절히 사용 (ㅋㅋ, ㅠㅠ, 😅, 😭 등)
- 목록 항목 앞에 아이콘으로 활용: 🆓, 📈, 💰, 🧓 등
- 기술 포스트에서는 최소한으로 (blockquote 안에서만)

## 어휘 선호

### 기술 용어
- 영문 기술 용어는 영어 그대로 사용: API, REST, JWT, Docker 등
- 한글 음차보다 원어: "시리얼라이저" → "Serializer" (단, 문맥에 따라 유연하게)
- 제품명은 공식 명칭 그대로: "Claude Code", "Mac mini", "GPT-4"

### 일상 용어
- 거창한 한자어보다 쉬운 말: "활용" → "쓰다/사용하다", "구축" → "만들다/세팅하다"
- 불필요한 수식어 제거: "매우", "정말로", "실질적으로" → 없애거나 구체적 수치로 대체
